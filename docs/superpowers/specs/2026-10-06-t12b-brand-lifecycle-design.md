# T12b — Brand lifecycle in the control panel

Status: approved by owner, 2026-10-06. Parent task: T12 / FUS-347. This is the first of two T12 follow-ups; T12c covers reporting and monitoring.

## Intent and success

An Employee should be able to enter a domain and default keyword, choose an already sealed landing template, start an install, and see whether the brand became READY or was rolled back. Operators need the actual Workflow status and step receipts, not a locally queued row presented as success. Employees may roll back a brand; only Owners may upgrade all brands. The add-brand checklist makes the owner-gated external setup visible without having the panel call LeadsGate or the VPS drain.

This design implements the T12 lifecycle portion of `docs/TASKS.md` and FA-1 through FA-4 in `docs/PRODUCT-BRIEF.md`. It preserves the approved role matrix and D1 ownership in `docs/plans/t12-control-panel.md`. No deploy, live Cloudflare mutation, LeadsGate call, drain call, or real Test sold is part of this coding task.

## Scope boundary

T12b includes draft creation, deployable revision creation, install and rollback dispatch, one canary-first upgrade-all command, lifecycle status and receipts, the four-item checklist, server-side role guards, and audit evidence. It includes the narrow factory/core integration and compensation repairs required for these actions to mean what the UI says.

T12c will handle the funnel report, alerts screen, mailing status, and any reporting-specific owner lead detail. T12b will not add new analytics event capture, mailing behavior, user management, a template builder, tenant bootstrap, or V1 lead-loss machinery. `spike/` and legacy port sources remain read-only.

## Ownership and interfaces

| Concern | Owner | Panel access |
| --- | --- | --- |
| Draft, revision, lifecycle status, step receipts, checklist and lifecycle audit | Factory D1 | Panel BFF binds factory D1; UI calls only the BFF |
| Live brand config, hostnames, account authorization, LeadsGate routing and lead/postback evidence | Core, in leads D1 | Panel and factory use separate private core Service Binding entrypoints; neither binds leads D1 |
| Template and form bytes | Sealed R2 artifacts | Factory Workflow only; the panel lists metadata from factory D1 |

The factory `brands` row is authoritative for `draft/installing/live/failed` and the deployed `current_revision_id`. Core `brand_runtime` is authoritative for live runtime settings. The BFF joins factory brands with core config and stats where present. It also keeps pre-existing core-only brands visible as `unmanaged` (read-only for lifecycle actions) until they have a factory record; it does not invent revisions for them. A draft or failed install is visible even when core has no usable runtime row; missing core runtime on a factory-live brand is shown as a sync error, never silently omitted or labelled READY. The existing core admin list/get contract remains a live-runtime API and is not stretched to represent drafts.

Create one private, factory-only core lifecycle entrypoint/operation for an idempotent runtime provision or revision switch. Public core `fetch` must continue returning 404 for administrative paths. The operation accepts a shared `brand_id`, installation account, normalized apex/www hostnames, `install_id`, expected current revision, target revision (nullable only for first-install detach), and only the runtime fields the factory is allowed to set. Core validates account and field shape, then compares the expected revision with the applied revision; a retry of the same `install_id` is a no-op, while another stale install is rejected. This permits an explicit rollback to an older revision without allowing a late install to overwrite it. Persist applied revision and last lifecycle install ID in core runtime. Add the missing `form_version` migration and set it to `form@<git_sha>` from the selected form artifact for operator visibility; this bundle identity is distinct from the lead payload's `form_version` (currently `2026-01`). Existing core-owned money-routing changes must not be silently overwritten by an install retry.

The initial runtime needs more than Domain + Keyword. Extend tenant-owned, validated deployment configuration to supply the account, LeadsGate AID and prepop base, form route, an Owner-approved default amount-bucket set, and the account credential mapping. The drain key is derived from the opaque brand ID, not employee input; the postback token remains unset until an Owner rotates/configures it. Correct the brand Worker's `CORE` binding to core's exported default fetch handler (the currently named `LeadsRpc` entrypoint does not exist). Provision a per-account `CORE_TOKEN` as a Worker secret, matched by a hash in core's `account_credentials`; never put its plaintext in factory D1, R2, receipts, source or the browser. The factory preflights the binding/secret and credential-account match and returns an actionable error through the BFF if anything is missing. No default comes from the browser or a cross-tenant database row. An Employee can therefore submit only Domain + Keyword + sealed-template selection without being allowed to alter money routing. The checklist still controls external launch readiness after the Worker install.

Core currently validates every lead against one tenant-wide payload `FORM_VERSION`. T12b permits a new sealed template, but an install/rollback/upgrade may select only a form artifact whose recorded payload version equals that core value. Add immutable payload-version metadata to form-artifact registration and reject missing or mismatched metadata at preflight; do not guess from its `form@<git_sha>` bundle ID. This preserves the existing submit validator and keeps cross-payload-version rollout outside T12b. Existing artifact records need an explicit verified metadata backfill before selection. A fake end-to-end submit test must prove the selected artifact's payload is accepted by core after install, upgrade and rollback.

## Flows

### Create draft

The UI offers a domain, default keyword and sealed template selector. The BFF normalizes and validates the apex domain and keyword, derives a display name from the domain, verifies the selected template version is sealed, selects the latest registered form artifact, and writes a `brands` row plus revision 1 in one factory D1 batch. If no sealed template or form artifact exists, creation is blocked with a concrete message. Duplicate domains return a conflict and do not create a second brand. The draft appears immediately in the factory-backed list. Draft creation does not deploy a Worker or claim that external routing is ready.

### Install and receipts

The BFF creates one `installs` row targeting that brand's revision and sends `{install_id, brand_id, revision_id}` to the factory `/install` command. A missing factory binding, non-2xx response or dispatch exception is an error, not `queued` success; persist a failed dispatch outcome for operator visibility and allow a safe retry using the same install ID where appropriate. The factory validates that the revision belongs to the brand and that template/form artifacts and tenant defaults exist before changing Cloudflare state.

The Workflow keeps the established validate → rollback snapshot → render → upload → deploy → attach → smoke sequence. On a first install it provisions the core runtime through the private binding before the first public domain attach. On an existing brand it switches the core revision after smoke. Its domain already points at the Worker during deploy, so there is a short new-Worker/old-core interval; T12b allows only template and form-bundle changes with the same RPC and payload versions, and the existing brand's core-owned hot settings remain unchanged through that interval. Tests exercise requests in this interval as well as after sync. Both paths verify core synchronization before marking the install `ready` and the factory brand `live`. The non-atomic interval between Cloudflare deployment and core D1 is covered by the existing rollback path, not called READY. Add named core-sync steps to the factory receipt schema and record their outcomes. The UI polls the install row and `install_receipts`, showing queued/running/ready/failed/rolled-back separately. READY means both the Worker smoke and core runtime sync succeeded; it does not mean the four-item external checklist is complete.

For a failure before mutation, preserve the previous live brand state. For a failure after mutation, insert a real compensation install row before launching rollback so its receipts have a valid parent; do not mark the original run `rolled_back` until compensation succeeds. On a failed first install, detach any newly attached Custom Domains and pause the core runtime, retaining its valid hostnames and audit/history; factory status remains `failed` so a retry is possible. On an existing brand, restore the previous deployed revision and its core runtime revision while preserving Owner-managed routing values. If compensation itself fails, surface `failed` with the recovery error and receipts; never imply successful rollback.

### Rollback

For a live brand the BFF resolves the previous deployed revision, creates a rollback install row and sends `{install_id, brand_id, to_revision_id}` to `/rollback`. If there is no earlier deployed revision, the target is explicitly `null` and means detach the domains, including when the current first install is already live. The factory validates any non-null target belongs to that brand, performs the rollback, synchronizes core runtime state, then advances factory status/pointer only after success. A successful detach leaves the factory brand `draft` with no current revision and core runtime paused, allowing a later reinstall. Employees and Owners may invoke this; the UI hides unavailable actions, while the BFF enforces the rule.

### Upgrade all

The Owner selects the currently deployed template version, a different sealed target version of the same template, a registered form artifact, and an eligible live canary brand. One BFF command invokes factory `/upgrade-all` once, with explicit `from_template_version_id`, `to_template_version_id`, `form_artifact_id`, `canary_brand_id`, and `started_by`. This resolves the current ambiguity where the same `template_version_id` is used both to select brands and to create their new revisions. The factory runs canary install and checks its READY state (including core sync) before starting the remaining eligible brands. A canary failure stops the fan-out; per-brand outcomes and receipts remain inspectable. No per-brand `/upgrade` route is invented.

## Checklist, authorization and audit

Show four checklist items for each brand: VPS drain route, LeadsGate Sold/Reject postback entries, Test sold producing a core `postback_events` row, and campaign Final URL suffix `keyword={keyword}`. Employees and Owners may record manual confirmation for the first, second and fourth items in a small factory D1 checklist table with actor and timestamp; this is attestation, not a service call. The Owner performs the external setup/test. For Test sold, either role may supply the opaque test `lead_id`; a private core query verifies a matching `soldLead` event joined to this brand and returns its event ID/timestamp. Only then is that event reference stored as verified checklist evidence. Wrong-brand or missing events are rejected, and repeating the same event is idempotent. It is not a checkbox that can be asserted without a postback. Do not store tokens, PII or free-form credentials in checklist rows. In local tests the core query is faked; real validation remains an owner-gated later operation.

Keep the approved role matrix: Employees can create/install, edit keyword, pause/resume and roll back; Owners alone can change buckets, A/B weights, flow gate, money routing and trigger upgrade-all. The BFF checks roles for every mutation. Factory/core lifecycle changes append audit entries with actor, action, target, before/after and time, including failed dispatch or compensation where relevant. The existing Audit screen includes these lifecycle entries; an API error is not recorded as a successful change.

## Validation and acceptance evidence

Implementation will use contract and Workflow tests with fake bindings/Cloudflare API; no real external calls. Acceptance evidence must include:

1. Employee creates a draft from Domain + Keyword + sealed template; it appears in Brands, with revision 1. Missing artifacts, invalid domain and duplicate domain are rejected.
2. Employee installs; exact command payload reaches factory, actual queued/running/ready/failed state and step receipts appear, and READY is impossible if core sync or smoke fails. Missing binding, non-2xx dispatch and thrown dispatch stay visibly failed/retryable, never falsely queued.
3. An existing-brand rollback uses an explicit previous revision; first-install rollback detaches domains. Failed compensation remains visibly failed. Employee and Owner can both roll back, including through the BFF role check.
4. Upgrade-all is Owner-only: Employee cannot see the control and gets server 403 if invoking its API; Owner launches exactly one canary-first factory Workflow with distinct source and target versions, and a failed canary stops fan-out.
5. Checklist confirmations persist and are audited; Test sold becomes complete only from a correctly branded postback event, with wrong-brand and replay cases tested. The Audit screen shows an Employee their own lifecycle actions and an Owner all actions. No test calls LeadsGate or the drain.
6. Factory-live/core-missing divergence and pre-existing core-only brands are visible; core never accepts a brand from the wrong account. The generated brand Worker can call core with its secret and correct binding. Brand Worker-served output contains no other brand identifiers, platform names, analytics key or DSN.
7. A fake lead submit succeeds after install, upgrade and rollback with a compatible registered form artifact; requests during the new-Worker/old-core interval remain compatible. Lifecycle UI tests cover actions and state transitions; API/Workflow tests cover authorization, payloads, idempotence, failures and receipts. `bun run typecheck` and `bun run test` pass before a PR is proposed.
